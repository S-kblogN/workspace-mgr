# Complete migration plan

This document records the complete migration from a repository-local Python
`sync` implementation and a large root `AGENTS.md` to the independently
released `workspace-mgr` CLI. Each phase represents a concrete change in the
deployed system. Development and verification are exit criteria within a phase,
not separate phases.

## Phase 1: build the complete software project

Only the public `workspace-mgr` repository changes.

- Build the Rust crate and CLI.
- Add the repository configuration and task-manifest schemas.
- Implement `init`, `instructions`, `doctor`, and `task create`.
- Implement `plan`, `publish`, `track`, `move`, `untrack`, `hydrate`, and
  `refresh`.
- Preserve the legacy `.chat-sync.json` schema and `sync` command syntax.
- Add isolated Git and local-DVC integration tests, version-aware verification
  tests, CI, documentation, and prerelease packaging.
- Produce native release-candidate archives for Linux x86-64/arm64 and macOS
  arm64/Intel as expiring workflow artifacts; do not create a public release.
- Apply the MIT License.

The existing workspace is read-only during this phase. The phase is complete
when the project builds, its test and lint suites pass, its package can be
assembled, and a reviewable release candidate exists. It is not published to
crates.io in this phase.

## Phase 2: replace the local sync engine without changing AGENTS.md

Build `workspace-mgr` manually and place the platform-specific binary in an
ignored local path inside the existing workspace, such as
`.workspace-mgr/bin/workspace-mgr`.

- Preserve the current root `AGENTS.md` unchanged.
- Move the Python implementation to an explicitly temporary legacy location.
- Replace the root `sync` entrypoint with a compatibility wrapper.
- Continue accepting existing `.chat-sync.json` files and command lines.
- Exercise a Git-only task, a DVC task, and a shared-checkout refresh.
- Keep an immediate route back to the legacy implementation.

The binary is not committed because it is a platform-specific build artifact.

## Phase 3: migrate repository policy and task scaffolding

Adopt a tracked repository configuration and generated agent instructions.

- Run `workspace-mgr init --adopt --profile shared-checkout`.
- Replace the large root `AGENTS.md` with the minimal bootstrap generated by the
  CLI.
- Review and tune the generic instruction modules selected by the repository
  config.
- Create all new work through `workspace-mgr task create`.
- Store runtime indexes and locks under the Git common directory rather than in
  each task directory.
- Leave historical tasks and legacy manifests unchanged.

The existing workspace still uses the manually built binary in this phase, so
instruction migration is isolated from public package distribution.

## Phase 4: publish the public package

Publish the already field-tested project under the MIT License.

- Confirm the crate name, package metadata, and public source inventory.
- Confirm no credentials, private paths, repository names, bucket names, or
  sensitive fixtures are present.
- Publish the crate to crates.io.
- Publish GitHub release binaries for supported macOS and Linux targets with
  checksums and release notes.

The existing workspace remains pinned to the manually built binary until the
public artifacts are independently verified.

## Phase 5: migrate the workspace to the public release

- Install and pin the public version through the host's managed package
  environment or `cargo install --locked`.
- Enforce the supported version range from repository configuration.
- Change the compatibility wrapper and CI to use the public installation.
- Remove the ignored development binary.
- Run `doctor`, `instructions`, `plan`, `publish`, and `refresh` against the
  installed package.

At the end of this phase, the workspace no longer depends on a development
checkout or manually copied executable.

## Phase 6: retire the legacy implementation

After the public package has completed representative real tasks:

- Remove the legacy Python implementation and local-binary scaffolding.
- Remove or turn the root `sync` wrapper into a time-limited deprecation shim.
- Stop generating legacy manifests.
- Migrate active manifests while leaving historical task directories intact.
- Retain legacy manifest reading in the public CLI only for the documented
  compatibility window.

This is the final removal of the immediate rollback path and therefore remains
an explicit migration decision.
